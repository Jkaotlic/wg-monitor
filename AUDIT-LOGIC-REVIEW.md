# wg-monitor — аудит логики проекта

**Дата:** 2026-06-20
**Объём:** весь репозиторий (~56 000 строк Go), компоненты `backend`, `agent`, `deploy`, `wg-monitor-cli`, `pkg/wire`, подсистемы подписи релизов и бэкапов.
**Цель:** найти дыры в логике — ошибки бизнес-логики, гонки, дыры авторизации, проблемы доверия/безопасности, ложные срабатывания мониторинга. Это аудит «на бумаге» (чтение кода), без запуска эксплойтов и без правок кода.

> Как читать. Каждая находка снабжена тройкой **Что / Как / Почему**:
> **Что** — в чём именно дефект; **Как** — как он проявляется или как его спровоцировать; **Почему** — почему это неверно (какое поведение ожидается). Указаны файлы и строки.
> Серьёзность: 🔴 Critical, 🟠 High, 🟡 Medium, ⚪ Low.

## 0. Краткая карта системы и модель доверия

Три компонента:

- **backend** (VPS, за Caddy/TLS): принимает отчёты агентов (`/v1/report`), раздаёт команды (`/v1/cmd` long-poll), принимает результаты (`/v1/cmd/result`), ведёт Telegram-бота (алерты, панели, топики), отдаёт dashboard и wizard-API для деплоя. Слушает **plain HTTP** на `127.0.0.1:8080` (`internal/backend/config.go:178`), TLS терминирует Caddy (`cmd/backend/main.go:354` — `ListenAndServe`, без TLS).
- **agent** (роутеры Keenetic/Entware): раз в минуту шлёт отчёт о здоровье туннелей/DNS/прошивки, исполняет команды бэкенда (диагностика, перезапуск туннелей, самообновление).
- **deploy** (машина оператора): SSH к VPS и роутерам, управление секретами, bootstrap агентов, шифрованные бэкапы и их восстановление.

Ключевые границы доверия, вокруг которых сосредоточены находки:
1. **agent → backend**: идентичность агента берётся из bearer-токена (хорошо — никнейм не подделать). Но **backend → agent** трастуется почти безусловно: агент исполняет команды и даже **меняет свой backend.url** по ответу бэкенда.
2. **Цепочка релизов** (GitHub → backend-mirror → agent): единственный криптокорень — ed25519-подпись `checksums.txt`, и она проверяется **условно**.
3. **Telegram callback-данные**: часть авторизации router-scoped действий завязана на привязку «топик → роутер», часть опасных действий — без одноразовых confirm-токенов.
4. **Caddy как доверенный фронт**: backend полагается на то, что Caddy вычищает `X-Forwarded-*`. Это допущение нигде не enforced.

## 2. 🔴 Critical

### SUP-1. Проверка подписи релиза условна — для текущего флота фактически отключена
**Файлы:** `internal/releasesig/signature.go:40-59` (`SignatureRequiredForVersion`), потребитель `internal/agent/actions/self_update.go:83-108`.

**Что.** Агент скачивает и проверяет `checksums.txt.sig` (ed25519) только если `SignatureRequiredForVersion(version)` вернул `true`. Эта функция делает «legacy carve-out»: для `v0.13.0-rc1..rc127` подпись НЕ требуется (`return n >= 128`, строка 52), и для версий ниже `v0.13.0-rc128` тоже. Интегритет бинаря в этом случае держится только на `checksums.txt`, который качается тем же каналом, что и сам бинарь.

**Как.** В README указано: «Latest RC used by the wizard flow: **v0.13.0-rc117**». То есть **весь текущий рабочий флот** запускает самообновление на версиях, где подпись не обязательна. Кто контролирует отдачу ассетов (компрометация GitHub-релиза, MITM на mirror-пути, см. SUP-2/SUP-3) — подменяет и бинарь, и `checksums.txt`; проверка `sha256` в `self_update.go:105` сверяет скачанный бинарь с **подменённым** же `checksums.txt` и проходит. Дополнительно: для пустой/непарсящейся версии функция возвращает `true` (безопасно), но любой путь, где классификатор версии вернёт `false`, обнуляет защиту.

**Почему.** Подпись — единственный криптокорень доверия к бинарю; гейтить её строкой версии нельзя. `checksums.txt` в модели угроз, ради которой подпись существует, контролируется атакующим. Подпись должна проверяться **безусловно**; legacy-исключение rc1..rc127 — это эксплуатируемый класс, а не просто заметка о совместимости.

### SUP-2. Релизный mirror `/v1/releases/download/{version}/{asset}` без аутентификации и без проверки подписи
**Файлы:** `internal/backend/release_proxy.go:16-66`, маршрут зарегистрирован вне `auth(...)` в `internal/backend/handler.go:397`.

**Что.** Все прочие `/v1/*` обёрнуты в `auth(...)`. Этот маршрут обёрнут только в `reqID(...)` — он **публичный**. Хэндлер слепо тянет ассет с GitHub (`releaseDownloadBase`) и стримит тело обратно, включая `checksums.txt` и `checksums.txt.sig`, **без какой-либо проверки**, что `.sig` валидирует отдаваемый `checksums.txt`.

**Как.** Mirror добавлен как доверенный origin для агентов (`releaseorigin.DefaultBackendMirrorBase`, разрешён в `self_update.go`). Backend — тупой pass-through: если его исходящий путь к GitHub скомпрометирован или GitHub отдал плохой релиз, mirror «отмывает» это во флот. Плюс открытый эндпоинт — это amplification исходящих запросов/трафика.

**Почему.** Раз mirror объявлен доверенным источником самообновления, он обязан **сам** проверять ed25519-подпись `checksums.txt` перед отдачей и быть за auth. В связке с SUP-1 это полноценный примитив для RCE по всему флоту.

### RET-1. Orphan-prune ретеншена удаляет живое состояние офлайн-инцидента
**Файлы:** `internal/backend/retention/policy.go:86-95`, во взаимодействии с `internal/backend/heartbeat/watcher.go:316-336` (`clearOfflineStateIfHard`) и `internal/backend/alerts/dispatcher.go` (`SendOffline`).

**Что.** Раз в сутки выполняется:
```sql
DELETE FROM incident_state WHERE (user_id, check_name) NOT IN (
    SELECT user_id, check_name FROM events WHERE ts >= ?   -- now-7d
)
```
То есть удаляются все строки состояния, у которых нет события за последние 7 дней. Но HARD-состояние офлайна живёт под `check_name='agent_heartbeat'`, и инцидент создаётся именно потому, что роутер **перестал слать отчёты** — новых событий по нему по определению нет. Guard `current_status != 'ok'` отсутствует.

**Как.** Роутер ушёл в офлайн → `SendOffline` пишет `incident_state(agent_heartbeat, status=hard)`. Агент больше не шлёт `agent_heartbeat`-события. Через 7 дней prune видит, что по этой паре нет свежих событий, и **удаляет живую HARD-строку**.

**Почему.** После удаления: realert `StaleHards` больше не видит инцидент; ack/silence оператора теряются; когда роутер вернётся, `clearOfflineStateIfHard` найдёт `current_status != 'hard'` и **не отправит recovery** — переход «офлайн→онлайн» молча проглатывается. Длинные аварии (самые важные!) теряют и алерт, и уведомление о восстановлении. Ретеншен не должен трогать состояние **активного** инцидента.

### RET-2. Окно orphan-prune (захардкоженные 7д) не связано с `EventsDays`
**Файл:** `internal/backend/retention/policy.go:73-95`.

**Что.** `prune` сначала удаляет события старше `EventsDays` (`PruneBefore`), затем удаляет `incident_state`, у которых нет события за **жёстко заданные 7 дней**. Окна несогласованы.

**Как.** Оператор ставит короткий `EventsDays` (например, 2 — маленький диск). Любая проверка, не репортившая последние `EventsDays`, теряет все свои события, поэтому 7-дневный подзапрос по ней пуст → её `incident_state` (возможно активный HARD) удаляется.

**Почему.** Окно orphan-prune должно быть гарантированно ≥ окна ретеншена событий, а активные строки (`current_status != 'ok'`) должны исключаться из orphan-prune полностью. Вместе с RET-1 это означает: ретеншен может стирать состояние именно тех роутеров, которые сейчас в аварии.

### SSH-1. Пароль SSH уходит на непроверенный хост при смене host-key (кража по MITM)
**Файлы:** `cmd/deploy/actions.go:838-883` (особенно 847), `cmd/deploy/ssh.go` (`ConnectSSHInsecureCaptureKey`).

**Что.** Когда host-key роутера **изменился** (`isHostKeyChangedErr`), `connectAgentSSHManaged` немедленно переподключается через `ConnectSSHInsecureCaptureKey(host, port, user, pass)`, чей `HostKeyCallback` принимает **любой** ключ. На этом соединении в качестве auth-метода передаётся **открытый пароль** роутера. Сверка MAC (строка 858) выполняется **после** аутентификации.

**Как.** Смена host-key — классический признак активного MITM. Код реагирует на этот признак тем, что подключается к подконтрольному атакующему эндпоинту и аутентифицируется реальным паролем — **до** проверки идентичности. Атакующий перехватывает пароль в ходе SSH-handshake; последующее несовпадение MAC (864) прервёт визард, но кредл уже утёк.

**Почему.** Порядок инвертирован: идентичность хоста должна проверяться **до** предъявления любого секрета. На legacy-SSH пути это утечка root-пароля роутера к MITM. (Связанная находка H3 из deploy-аудита: при отсутствии pinned MAC и существующего агента новый ключ принимается по одному `y/N`, причём `confirmAmbiguousTarget` для одиночного агента вообще не спрашивает — `actions.go:872-882`, `815-836`.)

### RST-1. Restore не сверяет хост из манифеста → затирание чужого VPS
**Файл:** `cmd/deploy/restore_backup.go` (поле `host` манифеста только печатается ~319-328, не сравнивается; `restoreBackupToCurrentVPS` ~376-401).

**Что.** Манифест бэкапа содержит поле `host`, но оно лишь выводится в preview. Restore заливает `state.db` + `backend.yaml` и стартует backend независимо от того, чей это архив.

**Как.** Навели визард на backend A, скормили бэкап backend B — молча перезаписали состояние A (включая Telegram chat/admin id и идентичность бота, запечённые в восстановленной БД).

**Почему.** Кросс-хостовый restore портит состояние и может перенаправить мониторинг/уведомления не того сервера. Поле идентичности есть — но guard, отклоняющий/предупреждающий о несовпадении, отсутствует.

### RST-2. Распаковка без лимита на plaintext-`.tgz` пути (tar/gzip-бомба → DoS диска)
**Файл:** `cmd/deploy/restore_backup.go:122` (цикл ~92-140).

**Что.** Известные члены архива (`state.db`, `backend.yaml`, `manifest.txt`, `agents.csv`) извлекаются через `io.Copy(f, tr)` из gzip-tar-ридера **без ограничения размера**.

**Как.** Сформированный/битый `.tgz` (gzip-бомба или огромный объявленный член) полностью разворачивается в `/tmp`, исчерпывая диск/иноды. Достижимо из интерактивного меню и `backup restore` CLI — до аутентификации содержимого.

**Почему.** Рядом существует `readArchiveMemberLimited` (`secrets_io.go:251`, `io.LimitReader`), используемый на зашифрованном/import-пути, но plaintext-restore его обходит — несимметрично, и одним архивом можно положить хост оператора.

### AGT-1. `pingcheck_toggle` идёт мимо awg-сессии → не работает на роутерах с авторизацией
**Файл:** `internal/agent/actions/pingcheck.go:85-120`.

**Что.** `primaryPingCheckToggle` сам строит `http.Request` и зовёт `c.HTTP.Do(req)` напрямую, минуя `awgmgr.Client.do()`/`ensureSession()`. Cookie `awg_session` не прикрепляется, login/`401`-retry handshake не выполняется (`client.go:50-91`).

**Как.** На любом роутере, где у awg-manager настроены логин/пароль (`SetCredentials` в `main.go:59-61`), `/api/pingcheck/toggle` вернёт 401/403. Код трактует это как «primary failed» и уходит в ndmc-fallback. То есть awg-manager-путь — мёртвый код на каждом роутере с авторизацией; toggle работает только через ndmc CLI (и только при верном `ndms_name`).

**Почему.** Двухуровневый дизайн «primary/fallback» молча деградирует в одноуровневый, а агрегированная ошибка маскирует реальную причину (нет сессии) под транспортную («HTTP_401»).

### AGT-2. Swap-скрипт самообновления может «окирпичить» агента
**Файл:** `internal/agent/actions/self_update.go:378-416` (особенно 384-385, 409-414).

**Что.** Скрипт делает:
```
cp -p <bin> <bin>.bak 2>/dev/null   # ошибки подавлены
mv <bin>.new <bin>
... если плохо:
mv <bin>.bak <bin>                  # rollback
```
`cp` в `.bak` подавляет **все** ошибки. Если `cp` упал (например, `/opt` переполнен — ровно сценарий малой памяти MIPSLE, ради которого проект и существует), скрипт всё равно делает `mv <bin>.new <bin>`. Если новый бинарь крэшит — rollback `mv <bin>.bak <bin>` двигает **несуществующий** файл, и `<bin>` исчезает полностью.

**Как.** `S99wg-monitor start` запускать нечего — агент окирпичен без пути удалённого восстановления (агент и есть способ доставить фикс). Нет и проверки, что `<bin>.new` существует/непуст перед `mv`.

**Почему.** Безопасный atomic-replace-с-rollback обязан убедиться, что бэкап создан, до перезаписи живого бинаря, и не перезаписывать, если шаг бэкапа провалился. Восстановление требует физического/SSH-доступа ко всему флоту.

### SUP-3. URL релиза наследует схему из `Backend.Domain` → downgrade HTTPS→HTTP
**Файлы:** `cmd/deploy/update_components.go:693-711` (`backendReleaseAssetURL`), `actions.go:1180-1190`, `awgm_deferred.go:417`.

**Что.** `backendReleaseAssetURL` парсит `state.Backend.Domain` и **сохраняет схему как есть** (`scheme = u.Scheme`), не прогоняя через `releaseorigin.normalizeRepoBase`, который форсит `https`. Если `Domain` = `http://…` (свободное поле `wizard.toml`), роутер тянет `checksums.txt` и бинарь по plaintext HTTP.

**Как.** Для версий, где подпись не обязательна (SUP-1), MITM на HTTP-загрузке подменяет и checksums, и бинарь; роутерный `sha256sum` сверится с подделкой и пройдёт. Даже для подписанных версий downgrade снимает транспортную защиту.

**Почему.** Проект намеренно форсит `https` в `normalizeRepoBase`, но этот билдер URL обходит проверку, возвращая ровно тот downgrade, против которого allowlist и вводили.

### TRUST-1. Агент мигрирует на любой `canonical_url` без пиннинга домена
**Файлы:** `pkg/wire/types.go:49-51`, `internal/agent/reporter.go:161-174`, `internal/agent/actions/update_backend_url.go:105-133`.

**Что.** Если ответ `/v1/report` содержит `canonical_url`, агент переписывает свой `backend.url` и перезапускается. `validateBackendURL` проверяет только: абсолютный, `https`, не localhost, не приватный IP. **Никакого allowlist/пиннинга** к текущему доверенному домену нет.

**Как.** Кто отвечает на `/v1/report` агента, возвращает `{"canonical_url":"https://attacker.example"}`. Health-check нового хоста (`update_backend_url.go:47-75`) лишь подтверждает 2xx на `/healthz` — тривиально для атакующего. Агент навсегда переезжает на чужой backend, который дальше выдаёт `self_update` (→ SUP-1/SUP-2 RCE) и любые команды.

**Почему.** Это переезд флота одним ответом без криптопривязки к прежнему бэкенду. Смягчение: агент общается с настроенным `backend.url` по HTTPS с валидацией сертификата, поэтому ответить может только легитимный бэкенд (или тот, кто сломал TLS). ### AUTH-1. Сравнение токена агента не constant-time; в лог 401 пишется хэш-префикс предъявленного токена
**Файлы:** `internal/backend/db/users.go:239-254` (`GetByToken`), `internal/backend/auth.go:35-47, 66-69`.

**Что.** Аутентификация агента ищет юзера через `WHERE token_hash = ?` (SQL-равенство по SHA-256 токена). `subtle.ConstantTimeCompare` (строка 249) выполняется лишь **после** успешного матча и ничего не добавляет — реальное сравнение это SQL `=`, оно не constant-time. Сам комментарий называет ветку «paranoia». Параллельно `logUnauthorized(..., presented)` (`auth.go:69`) пишет в WARN 12-hex-символьный префикс SHA-256 **предъявленного** токена на каждый 401.

**Как.** Существование токена решается индекс-равенством по хэшу. Прямой timing-атаки на сырой токен нет (хэш высокоэнтропийный), но лог 401 даёт стабильный отпечаток каждого подобранного токена тому, кто читает логи — оракул различимости. Несогласованность: wizard и dashboard корректно используют `subtle.ConstantTimeCompare` против известного секрета, а агентский токен — нет.

**Почему.** Токен агента — основной кредл флота. Сравнение должно быть hash-then-constant-time против хранимого хэша без утечки match/no-match через структуру запроса, а аудит 401 не должен логировать производную предъявленного секрета.

### HB-1. Resume-grace (90с) короче времени первого полного отчёта → ложный OFFLINE
**Файлы:** `internal/backend/heartbeat/watcher.go:221-251`, дефолт `ResumeGraceSec=90` (`config.go:234-236`), `MarkResumed` зовётся из `handler.go:581`.

### HB-2. `SendOffline` затирает ack/silence оператора
**Файл:** `internal/backend/alerts/dispatcher.go:256-264`.

### HB-3. RMW над `agent_heartbeat` без условного UPDATE → гонка с диспетчером и realert
**Файлы:** `internal/backend/heartbeat/watcher.go:316-336` (`clearOfflineStateIfHard`), `dispatcher.go:256`, FSM Noop/Soft-путь `handler.go:705-748`.

**Что.** `clearOfflineStateIfHard` делает `Get` → правка в Go → `Save` для `agent_heartbeat` без транзакции/блокировки строки. Параллельно ingest отчёта может вызвать `SendOffline` (полный Save) или realert — `BumpLastAlertAt`. SQLite пиннит один коннект (`SetMaxOpenConns(1)`), поэтому отдельные стейтменты сериализуются, но read-modify-write **не атомарен**.

**Как.** Watcher прочитал HARD, решил очистить; тем временем stale-отчёт/renotify пишет новый HARD с новым `HardSince`; последующий `Save` watcher-а перетирает его обратно в OK (или наоборот) — флаппинг, потеря переходов online/offline, пропущенный RECOVERY. Аналогично, Noop/Soft-`Save` из обработчика отчёта может затереть `last_alert_at`, обновлённый realert-ом между `state.Get` и `Save`, → преждевременный повторный алерт.

**Почему.** Переходы состояния общей строки должны делаться одним условным `UPDATE ... WHERE current_status='hard'` (как уже сделано в `BumpLastAlertAt`/`SetLastAlert`), а не Go-side RMW, который перетирает конкурентную запись.

### AGT-3. Реплей деструктивных команд после истечения 10-мин кэша
**Файлы:** `internal/agent/cmdloop/loop.go:76, 129-163`, диспетч `internal/agent/actions/runner.go`.

### AGT-4. Staleness handshake (180с) FAIL-ит здоровые простаивающие туннели
**Файл:** `internal/agent/checks/tunnels.go:298-312`, константа `defaultHandshakeMaxAge=180s`.

**Почему.** Возраст handshake используется как прокси-liveness, но каденция handshake в WireGuard управляется трафиком, а не heartbeat-ом. Нужна корроборация (провал PingCheck или застой rx/tx) прежде чем объявлять stale-handshake падением.

**Почему.** Confirm-токен должен фиксировать ровно ту пару (key, country), на которую согласился пользователь: разрешать ключ **до** консумации и отклонять confirm с пустым ключом, иначе выдаётся `.conf` для другого аккаунта.

### TG-M4. Привязка confirm-токена к актору опциональна; `restore()` перевзводит консумированный токен
**Файл:** `internal/backend/callbacks/confirm_tokens.go:33-40, 55-57`.

**Что.** `consume` проверяет идентичность актора только при `ActorTGID != 0` — токен без актора консумится любым, кто совпал по user/action/target/thread. `restore` переинициализирует тот же консумированный токен без пометки used → снова окно реплея.

**Почему.** Привязка к актору для опасных подтверждений должна быть обязательной (fail-closed при `ActorTGID == 0`); консумированный одноразовый токен должен быть терминальным — restore обязан выпускать свежий.

### TG-M5. `handleAmneziaDownloadAsk` пропускает валидацию и разыменовывает `info` после непроверенного пустого ключа
**Файл:** `internal/backend/callbacks/amnezia_premium.go:398-437`.

**Что.** В отличие от соседних хэндлеров, этот не зовёт `GetByID(args.UserID)`, игнорирует ошибку `getAmneziaKeyByID`, затем сразу `fetchAmneziaAccount(ctx, key)` и разыменовывает `info.*`. Нет guard `if key == ""` (который есть в confirm-варианте).

**Почему.** Stale-панель с удалённым ключом даёт `key == ""`, отправляя пустой кредл в Amnezia API; на части форм ошибок `info` используется без guard, на который опирается остальной пакет.

### CMD-M1. Команда может «утечь» из очереди при отмене контекста между pop и issue
**Файл:** `internal/backend/cmd/queue.go:323-362`.

**Что.** `Dequeue` извлекает `head` из `pending` и лишь затем проверяет expiry/пишет в `issued`. Если контекст HTTP уже отменён, команда удалена из `pending`, записана в `issued` и возвращена, но агент (с отменённым long-poll) её не получает. Команда не pending и не доставлена; чистится по TTL, а тап оператора молча потерян без `onDrop`.

**Почему.** Команда, удалённая из очереди, но не доставленная, должна реквеуиться или репортиться через `onDrop`, а не молча консумиться. (Документировано как «оператор перетапнет», но это реальная дыра доставки.)

### AGT-M1. `persistResultCache` не очищает файл кэша → результаты «воскресают» после рестарта
**Файл:** `internal/agent/cmdloop/loop.go:254-257`.

**Что.** `persistResultCache` рано выходит при `len(l.resultCache) == 0`, поэтому при опустошении кэша файл на диске не перезаписывается и хранит прошлый снимок. После рестарта `loadResultCache` перечитывает устаревший файл; entries в пределах TTL воскресают.

**Почему.** Персист и in-memory расходятся; «пустое» состояние не персистится. В связке с AGT-3 ранее исполненная-и-вытесненная команда может переотдать результат из файла, который должен был быть очищен.

### AGT-M2. Долгие действия блокируют единственную горутину командного канала
**Файл:** `internal/agent/actions/runner.go:90-124` (`DiagNow`).

**Что.** `DiagNow` опрашивает до ~36с (`DiagPollMax`×`every`), команда диспатчится под контекстом cmdloop без per-command таймаута. Один `diag_now` держит горутину ~36с, в течение которых новые команды не поллятся.

**Почему.** Долгое действие блокирует единственную горутину; агент не может обработать другую команду (включая abort/`force_recheck`). Команды должны исполняться с ограниченным per-command контекстом.

### AGT-M3/M4. Несогласованная нормализация статуса и тихий «no update» при дрейфе парсера
**Файлы:** `internal/agent/checks/tunnels.go:300-301`; `internal/agent/actions/maintenance.go:50-99`.

**Что.** `tunnelFailReasons` сравнивает `tu.Status != "running"` case-sensitive, тогда как все соседи нормализуют `strings.ToLower(strings.TrimSpace(...))` (и принимают `"connected"` как здоровый). А `parseComponentsList` хардфейлит только при пустом `localVersion`; при переименовании блока `firmware:` `firmwareVersion` остаётся пустым → «обновлений нет» молча.

**Почему.** Путь отказа строже пути здоровья (биас к ложным «туннель упал»); дрейф парсера прошивки даёт ложноотрицательный «всё актуально» без ошибки.

## 5. ⚪ Low (кратко)

- **CMD-L1 / AGT-L1.** In-place компакция `slice[:0]` над данными, достижимыми из map (`cmd/queue.go:154-169`, `callbacks/amnezia_secrets.go:241-273`, `hidemy_secrets.go:219-251`). Сегодня корректно, но хрупко при шаринге backing-массива/будущих полях-указателях. Лучше `append` в свежий `make(...)`.
- **AGT-L2.** Floor джиттера backoff = 1мс (`cmdloop/loop.go:289-314`): ~0.1% ретраев при постоянно офлайн-бэкенде срабатывают через ~1мс несмотря на cap.
- **AGT-L3.** `parseChecksum`-путь форматирует `wantSha[:16]` без проверки длины (`self_update.go:105-107`): битый `checksums.txt` с коротким первым полем → panic в ветке ошибки, способный убить горутину cmdloop.
- **DEPLOY-L1.** Passphrase/ключевой материал не зануляется (`encrypted_restore.go`, `backup_actions.go`, `internal/backup/crypto.go`) — экспозиция через core dump/swap.
- **DEPLOY-L2.** Argon2 параметры низковаты (`t=1, m=64MiB`) — приемлемо только потому, что passphrase 256-бит случайный; опасно при человекочитаемом пароле.
- **DEPLOY-L3.** Generic-билдеры удалённых команд (`apt-get install -y <pkg>`, `command -v <cmd>`) неэкранированы (`actions.go:2439-2444`) — сегодня только литералы, но injection-prone при переиспользовании.
- **DEPLOY-L4.** Валидация `backend.yaml` на import слабее, чем на restore (`restore_backup.go:232-247`): `db_path`/`bot_token_file` куда угодно — латентно при расширении import.
- **TG-L1.** Обрезка toast/error по байтам (`router.go:632-634, 644-658`) рвёт UTF-8 рун кириллицы → TG может отклонить тост (не паника).
- **TG-L2.** Delete-хэндлеры репортят успех для уже отсутствующих ключей/кодов (`amnezia_secrets.go:120-147`, `hidemy_secrets.go:118-145`).
- **TG-L3.** Имя туннеля Premium/HideMy не санитизируется (`amnezia_premium.go:474-482`, `hidemyname.go:308-318`) — асимметрия с self-hosted путём.
- **TG-L4.** Сырой текст ошибки upstream утекает в TG через `shortToast(err)` — возможно эхо access-кода/`vpn://`-ключа.
- **TG-L5.** Парсер self-hosted KV (`selfhosted_amnezia.go:458-524`) рвёт значения с пробелами/`=` → неверные SSH-креды с вводящим в заблуждение «saved».
- **TG-L6.** `realert` рендерит «reminder #0» при скосе часов (`poller.go:219`).
- **TG-L7.** Digest показывает 🟢 для пустого флота «0 из 0» (`poller.go:143-150`).
- **TG-M2-realert.** Per-chat 429 прерывает весь батч realert и гейтит весь поллер (`poller.go:175-177, 254-257`) — голодание не связанных чатов.
- **DEPLOY-L5.** `ForgetKnownHostInteractive` (`known_hosts_cmd.go:183-282`) позволяет тихий re-TOFU для alias, не известного загруженному state.
- **VER-L1.** `FirmwareNewerThan` (`upstream/compare.go:114-146`) при смешанных числ./буквенных сегментах падает в лексикографику (`"9" > "10"`) — риск ложного/пропущенного предупреждения о прошивке.
- **DB-L1.** `KVRepo.Get` возвращает `("", err)` при ошибке скана — приглашение трактовать сбой как «ключ отсутствует» и переотправить one-shot уведомление (`db/kv.go:13-20`).
- **MIG-L1.** Дедуп миграции `MIN(id)` (`db/db.go:112-120`) при ретрае с тем же `ts`, но разным статусом произвольно выбирает первую вставку.
- **TZ-L1.** Soft-flap бакетируется по UTC (`dispatcher.go:62`), а digest — по MSK (`mscLoc()`): флапы 00:00-03:00 MSK уходят в «вчера» по UTC.

## 6. Собственные наблюдения по оркестрации backend (`cmd/backend/main.go`)

- **LIFE-1 (⚪).** `notifyDegradation` оборачивает только `callbacks router` и `realert poller` (строки 319-337). `watcher.Run` (287), `retentionPolicy.Run` (299), digest (348) и janitor (304) — без неё. Смягчение: `watcher.Run` не возвращает ошибку и завершается только по `ctx.Done()` или панике (паника = краш процесса = громкий отказ, systemd рестартует). Так что «тихая смерть» watcher-а маловероятна, но **асимметрия мониторинга горутин стоит выровнять**.
- **LIFE-2 (⚪).** Грейсфул-shutdown ждёт только `watcher.WaitForExit()` и `rp.WaitForExit()` (364-365), но не callbacks/retention/digest/janitor. На SIGTERM их горутины обрываются по ctx без ожидания — для in-memory воркеров приемлемо, но retention в середине VACUUM/checkpoint может оборваться.
- **LIFE-3 (⚪).** `SetMyCommands*` используют один общий 5-секундный контекст на несколько последовательных сетевых вызовов (91-114): если первый медленный, последующим достаётся меньше времени. Некритично (все non-fatal).

## 7. Что проверено и признано корректным (чтобы не было ложных тревог)

- **Идентичность агента** в `/v1/report`, `/v1/cmd`, `/v1/cmd/result` берётся из контекста токена, не из клиентского никнейма — один роутер не может репортить/поллить за другого (`handler.go:574-575, 860-861, 926-927`).
- **Wizard/dashboard токены** сравниваются `subtle.ConstantTimeCompare` (`wizard_handler.go:76`, `dashboard_handler.go:48,178,234`).
- **Лимиты тела:** report 64 KiB, result 1 MiB, wizard JSON 64 KiB, proxy 64 MiB; JSON-декодеры отклоняют trailing data.
- **`ed25519.Verify`** используется корректно (не `==`), длина подписи проверяется (`releasesig/signature.go:18-26`).
- **Ingest событий** транзакционен с `INSERT OR IGNORE` идемпотентностью (`handler.go:607-663`).
- **SQL** параметризован везде; LIKE-prefix корректно экранирует `_`/`%`/`\` с `ESCAPE '\'`.
- **Wizard-команды** на жёстком allowlist + `sanitize*` с диапазонными проверками; `update_backend_url` намеренно убран из dashboard-allowlist (`wizard_handler.go:596-600`).
- **Крипто бэкапов:** XChaCha20-Poly1305, свежие salt+nonce на вызов, JSON-заголовок как AAD; на зашифрованном/import-путях есть guard от path traversal (ведущий `/`, `..`, симлинки). Дыра — именно plaintext-restore (RST-2).
- **Wizard-API SSH fallback** (`vps_sync.go`): токен через stdin в `chmod 600` tmpfile, `shellSingleQuote` везде — токен не на argv.
- **`aclAllow`** корректно связывает топик→thread→chat→владелец/оператор для router-scoped callback (исключение — глобальный self-hosted store, TG-1).
- **Атомарная запись state** визарда: temp-file + rename `0600` (`state.go:96-113`). PID-lock без явного TOCTOU.
