# 2026-08-19 Сверка модулей со свежим awg-manager (2.17.2+r15)

Роутер за сутки прошёл `+r5 → +r12 → +r15`. Спека — `GET /api/openapi.yaml`,
365 эндпоинтов; наш код зовёт 42. Проверка только чтением, кроме одного
`POST` на несуществующий адрес (он и так возвращает 404).

## Что проверено

Каждый адрес, который дёргает `internal/agent/awgmgr`, опрошен на живом
роутере. Все живы: `200` на чтении, `405` на тех, где мы и так шлём POST.

## Дыра, которую закрыли

**`POST /api/pingcheck/toggle` → 404. Эндпоинта больше нет.**

Вместо него появилась пара per-tunnel адресов:

```
POST /api/tunnels/pingcheck?id=<tunnel>          — включить сторож
POST /api/tunnels/pingcheck/remove?id=<tunnel>   — снять
GET  /api/tunnels/pingcheck?id=<tunnel>          — прочитать состояние
```

Пока код бил в старый адрес, `pingcheck_toggle` держался на запасном пути
через `ndmc interface <ndms_name> ping-check`. У **opkg-туннелей ndms_name
нет вовсе**, то есть для половины туннелей флота действие было сломано
целиком — и молча: пользователь видел ошибку про ndmc, а не про исчезнувший
эндпоинт.

Почему не заметили раньше: собственный тест
`TestPingCheckToggle_PrimaryPathOK` прибивал мёртвый адрес и был зелёным.
Тест, сверенный с реальностью один раз и не пересверяемый, — это не защита,
а фиксация вчерашней правды.

Исправлено: штатный путь переведён на per-tunnel адреса; запасной путь через
ndmc остаётся для старых сборок, но при пустом `ndms_name` теперь честно
говорит, что адресовать нечем, вместо вызова с пустым именем интерфейса.

## Новое, что меняет планы

**`GET /api/tunnels/traffic?id=&period=` — история трафика по туннелю.**
Отдаёт ряд точек `{t, rx, tx}`. Проверено вживую на `awg11` за 24 часа.

Фаза F программы («агент считает байты») этим отменяется: роутер уже ведёт
ряд сам, агенту остаётся его забрать. Работы там на порядок меньше, чем
закладывалось.

**`GET /api/hydraroute/geo-expand?kind=&tag=` — разворачивает гео-тег в домены.**
`geosite:OPENAI` разворачивается в `.chatgpt.com`, `.openai.com`,
`.oaistatic.com` и далее.

Это снимает возражение, из-за которого поиск «куда пойдёт этот домен» был
отклонён: я предупреждал, что честно ответить нельзя, потому что правила
вида `geosite:OPENAI` доменом не ищутся. Теперь ищутся.

**`POST /api/tunnels/replace?id=` — замена конфига туннеля на месте.**
Мастер замены конфига (фаза D2) закладывался на «импортировать новый туннель
рядом, переключить маршрутизацию, старый выключить». Замена на месте — другой
и более короткий сценарий. Требует отдельного решения: он проще, но теряет
свойство «прежний туннель остаётся для отката».

## Что ещё есть и не используется

`/routing/resolve` (домен → IP, обычный резолв), `/hydraroute/geo-tags`,
`/hydraroute/ipset-usage`, `/hydraroute/oversized-tags`, `/hydraroute/policy-order`,
`/control/start`, `/control/stop`, `/control/toggle-default-route`,
`/tunnels/export`, `/tunnels/export-all`, `/system/update/{check,apply,changelog}`,
целое семейство `/singbox/router/*` и `/singbox/fakeip/*`.

Ни одно из них не закрывает известной дыры; это материал для будущих фаз.

## Вывод

Одна дыра в работающей фиче — закрыта. Три находки, меняющие план: трафик
готов на роутере, гео-теги разворачиваются, замена конфига делается одним
вызовом. Спека роутера обновляется чаще, чем мы к ней ходим, — сверку стоит
делать в начале каждой фазы, а не раз в полгода.
