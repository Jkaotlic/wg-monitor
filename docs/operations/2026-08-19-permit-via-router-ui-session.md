# 2026-08-19 Permit в родном UI роутера: открытый вопрос закрыт

## Что проверяли

Открытый вопрос из `2026-08-18-routing-truth-live-session.md`: `POST
/api/access-policies/permit` отвечал `success:true` и **не менял цепочку**
политики. Обе пробы тогда били в `Bridge1` (мост), продакшен-путь в мост
не целится никогда, поэтому корректная формулировка была «permit не
проверен на туннеле», а не «permit не работает».

Способ, записанный тогда как дешёвый: добавить интерфейс в политику из
**родного веб-интерфейса awg-manager** и посмотреть, изменится ли цепочка.
Сделано здесь — браузером (headless Chromium, Playwright), кликами по
живому UI, с записью всех запросов, которые UI шлёт.

Слой 4 (эксплуатация): TDD не применяется, работает диагностика до мутации и
проверка постусловия.

Роутер: Keenetic KN-1811, `5.01.C.3.0-1`, awg-manager **2.17.2+r12**
(на 18.08 было `+r5` — роутер обновился сам), `http://192.168.0.1:2222`,
авторизация из LAN не требуется.

## Проба 1: мост `Bridge1` → политика `HydraRoute`

Состояние до (чтение мимо кеша, `?refresh=true`, и кешированный путь — совпали):

```
HydraRoute: OpkgTun11(0) -> Wireguard0(1) -> OpkgTun10(2)
RU:         GigabitEthernet1(0)
```

Клик «Добавить» → «Guest network (Bridge1)» в UI роутера. Запрос, который
UI отправил сам:

```
POST /api/access-policies/permit
{"name":"HydraRoute","interface":"Bridge1","order":3}
→ 200 {"success":true,"data":{"ok":true}}
```

`order:3` = длина цепочки. **Это буква в букву тот же запрос, что шлёт наш
`addTunnelToHydraRoutePolicies`.**

Постусловие через 2 с и через 7 с, обоими путями чтения:

```
HydraRoute: OpkgTun11(0) -> Wireguard0(1) -> OpkgTun10(2)   -- Bridge1 отсутствует
```

Цепочку не изменил и **собственный экран роутера**: список интерфейсов
политики после клика остался из трёх строк. Откат
(`DELETE .../permit?name=HydraRoute&interface=Bridge1`) выполнен, diff с
исходным состоянием пуст.

## Проба 2: туннель `OpkgTun10` → политика `RU`

Та же операция на **туннельном** интерфейсе — это и есть форма, которую
использует продакшен-путь. Мишень выбрана так, чтобы мутация не могла
изменить текущую маршрутизацию: `OpkgTun10` — это `awg10`, он выключен
(`status:"disabled"`), а в цепочке `RU` он встаёт **после** живого
`GigabitEthernet1`, то есть резервом, который не активируется.

```
POST /api/access-policies/permit
{"name":"RU","interface":"OpkgTun10","order":1}
→ 200 {"success":true,"data":{"ok":true}}
```

Постусловие — **выполнено**:

```
RU: GigabitEthernet1(0) -> OpkgTun10(1)
```

Подтверждено тремя источниками: чтением мимо кеша (`?refresh=true`),
кешированным `GET /api/routing/access-policies` и самим экраном роутера
(«1 Подключение Ethernet», «2 awg3-main-work (OpkgTun10)»).

Откат `DELETE .../permit?name=RU&interface=OpkgTun10` → `success:true`,
чтение после отката:

```
HydraRoute: OpkgTun11(0) -> Wireguard0(1) -> OpkgTun10(2)
RU:         GigabitEthernet1(0)
```

diff с исходным состоянием — **пусто**. Роутер восстановлен.

## Вывод

- **permit работает** — на туннельном интерфейсе, то есть ровно там, где им
  пользуется код. Молчаливый no-op воспроизводится только на мосте
  (`Bridge1`), и воспроизводится в том числе из родного UI роутера, то есть
  это ограничение роутера, а не дефект нашего клиента.
- Наш запрос идентичен запросу UI, включая `order = len(chain)`. Чинить в
  коде нечего.
- `DELETE` permit тоже работает и проверен постусловием — откат в фазе C
  можно строить на нём.
- Проверка постусловия в `addTunnelToHydraRoutePolicies` (перечитать мимо
  кеша, а не верить `success:true`) остаётся оправданной: на мосте API
  именно так и врёт.

Шаг «сделать главным» фазы C можно проектировать на permit. Единственное
ограничение, которое стоит держать в голове: интерфейсы-мосты в цепочку не
добавляются, и API об этом не сообщает.

## Сверка чтения на r12

`AWGM_URL=http://192.168.0.1:2222 go test -tags manual
./internal/agent/actions/ -run LiveRouteSnapshot -v` → PASS. Снимок на r12
совпал с ожиданиями: политика `HydraRoute` — 26 правил, активное звено
`OpkgTun11` → `awg11`, два звена `unavailable`; политика `RU` — 2 правила,
без `active_tunnel_id` (мимо VPN); 28 правил, ни одного без привязки.

Побочная находка, из-за которой на табе «Маршруты» врал бейдж: в снимке
`enabled` у выключенного туннеля приезжает `true`. Так и задумано —
`buildRouteSnapshot` дожимает его из каталога маршрутизации NDMS
(`route_status.go:190`, `Enabled || ep.Enabled`), чтобы выключенный туннель
оставался мишенью для переноса правил. Судить о том, работает ли туннель,
можно только по `status`. Учтено в `tunnelLive` (`miniapp/src/routes.js`).
