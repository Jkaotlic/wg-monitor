## 0. Что это за система (восстановленное намерение)

Self-hosted мониторинг и удалённое управление парком роутеров **Keenetic + AmneziaWG**. Монорепо `github.com/Jkaotlic/wg-monitor` (Go 1.26.4, ~100k строк, 29 пакетов), 3 компонента:

- **backend** — сервис на Linux VPS за Caddy/TLS. Принимает поминутные отчёты агентов (SQLite, `modernc.org/sqlite`), шлёт Telegram-алерты, рендерит control-панели (туннели, маршруты, диагностика, обслуживание, операторы, Premium, обновления), web-dashboard.
- **agent** — на каждом роутере (MIPSLE softfloat / ARM64, UPX, лимит RAM ≤64 MB). Собирает состояние, шлёт отчёты по HTTPS, поллит команды, исполняет их как root (route add/delete/rebind, opkg, self-update, tunnel import).
- **deploy** — CLI-визард оператора. Бутстрап агента через AWG Manager / VPS-relay, установка/обновление backend по SSH, шифрованные бэкапы и disaster recovery.

Доставка: GitHub Releases (последний `v0.13.0-rc133`). Контракт agent↔backend — `pkg/wire`.

## 3. НАХОДКИ

### SEC-01 — Подпись релизов: исключение для `v0.13.0` / rc<128 `[High, условный блокер выпуска stable]`

- **Где:** `internal/releasesig/signature.go:40-56` (`SignatureRequiredForVersion`), вызовы в `internal/agent/actions/self_update.go:83-91`, `cmd/backend/backend_update_cli.go` и `cmd/deploy/github.go` (все три через один и тот же `releasesig`).
- **Что подтверждено:** инфраструктура подписи реальна и корректна. Ed25519, публичный ключ зашит (`signature.go:12`), `VerifyChecksumsSignature` (`:18-26`) проверяется **до** сверки SHA (`self_update.go:88`), hard-fail при отсутствии/невалидности `.sig`. Release-workflow реально подписывает (`release.yml:148-153`: `test -n SEED` + `release-sign`). Для текущего rc133 `SignatureRequiredForVersion` → `true` (rc≥128).
- **Брешь:** `signature.go:45` — `if strings.EqualFold(version, "v0.13.0") { return false }`. Для **точной** строки `v0.13.0` подпись НЕ требуется; для `v0.13.0-rcN` при N<128 — тоже. В `self_update.go` **нет защиты от даунгрейда** (проверено grep'ом — сравнения target vs current нет).
- **Сценарий:** атакующий компрометирует GitHub-аккаунт `Jkaotlic` (или backend, выдающий `self_update`) → публикует/указывает вредоносный `v0.13.0` (точная строка) + согласованный `checksums.txt` без `.sig` → агенту приходит команда обновиться на `v0.13.0` → подпись пропускается (исключение) → SHA сходится (его же checksums) → **RCE как root на парке**. Origin-whitelist не спасает: для этого вектора origin легитимен (сам GitHub-релиз).
- **Сейчас не эксплуатируется:** финального `v0.13.0` ещё нет (только rc-теги), rc<128 — старьё. Брешь латентная — «выстреливает» в момент выпуска stable `v0.13.0` или если агента удаётся навести на старый unsigned rc.
- **Фикс:** убрать спец-исключение для `v0.13.0` (подписывать stable так же, как rc128+) либо явно зафиксировать как принятый риск + гарантировать, что финальный `v0.13.0` публикуется только подписанным и клиент его требует. Опционально — отклонять даунгрейд на версию ниже текущей в `self_update`.

### SEC-02 — TLS к AWG Manager: нет cert-pinning, есть break-glass `[Medium]`

- **Где:** `cmd/deploy/awgm_client.go:71-76` (HTTP) и `:261-267` (websocket) — `InsecureSkipVerify:true` при `AWGM_INSECURE_TLS=1`; `cmd/deploy/awgm_relay.go:376-379` — Python relay `ssl._create_unverified_context()` только при `insecure_tls_enabled(cfg)`.
- **Что подтверждено:** прошлый блокер (безусловный обход TLS в Python) **закрыт** — теперь default `ssl.create_default_context()`. Небезопасный режим в обоих путях гейтится явным флагом, помечен `#nosec G402` с пояснением. Но **позитивного pinning нет**: оператор с самоподписанным сертом KeenDNS включит `AWGM_INSECURE_TLS=1` → на пути оператор/VPS→AWG Manager возможен MITM с утечкой `APIKey`/`TerminalPassword`/WG-конфигов → root на роутере.
- **Фикс:** TLS-pinning по fingerprint (TOFU, переиспользовать паттерн SSH known_hosts из `ssh.go`); небезопасный режим — только разово с громким предупреждением, не «прилипающим» env во весь сеанс.

### SEC-03 — Секреты сторонних сервисов в plaintext at-rest `[Low]` (ср. старый SEC-05)

- **Где:** `internal/backend/callbacks/amnezia_secrets.go` (VPN-ключи), `hidemy_secrets.go` (access-codes) — JSON, mode 0600 root, без шифрования.
- **Оценка:** файлы 0600, атомарная запись — корректно. Но при LFI/read-доступе к VPS утекают все активные VPN-ключи парка. Risk-приёмка возможна (full-disk encryption / 0600), но envelope-шифрование надёжнее.
- **Фикс:** envelope-шифрование at-rest (ключ из passphrase в памяти/OS keyring), либо явно задокументировать требование LUKS на VPS.

### SEC-04 — Wizard ходит в GitHub API без аутентификации `[Low]`

- **Где:** `cmd/deploy/github.go` — `GetLatestRelease`/`GetAsset` без `Authorization`; `Cache-Control: no-cache`, без кэша Release в сессии.
- **Сценарий:** `update-all` на несколько агентов из офиса за NAT → лимит 60/час → 403 с невнятной ошибкой.
- **Фикс:** поддержать `GITHUB_TOKEN` (header при наличии); кэшировать Release в рамках сессии.

### SEC-05 — Dashboard-сессия без отзыва `[Low]` (ср. старый NEW-02, частично закрыт)

- **Где:** `internal/backend/dashboard_handler.go` — cookie = HMAC(token, "…:"+expiryUnix), TTL 12ч, exp проверяется на сервере; HttpOnly+SameSite=Strict+Secure.
- **Оценка:** прошлая претензия (вечный токен) **закрыта** — добавлен exp. Остаётся: нет серверного отзыва конкретной утёкшей сессии до истечения 12ч. Для малого ops-инструмента приемлемо.
- **Фикс (опц.):** серверный список отозванных или версия сессии в HMAC.

### BE-01 — VACUUM in-place блокирует единственный writer `[Medium]`

- **Где:** `internal/backend/retention/policy.go:103-117` — `maint.ExecContext(ctx, "VACUUM")` (in-place) на отдельном коннекте, но файловый exclusive-lock SQLite блокирует основной пул (`db.go` `SetMaxOpenConns(1)`, `busy_timeout(5000)`).
- **Сценарий:** на большой БД VACUUM держит lock минуты → `/v1/report` ловят `SQLITE_BUSY` → 5с timeout → 500 → heartbeat-watcher видит «тишину» → ложные OFFLINE по парку.
- **Смягчение:** дефолт `VacuumInterval=168h` (еженедельно, `config.go:297`) — событие редкое.
- **Фикс:** `VACUUM INTO` + атомарный rename, либо `auto_vacuum=INCREMENTAL`. Логировать длительность (уже есть).

### BE-02 — Неограниченный goroutine-fanout на hot-path `[Medium]`

- **Где:** `internal/backend/handler.go:553` (wake на resume), `:751` и `:1041` (deferred-update) — `go func()` на каждое событие, без семафора/worker-pool (grep по `semaphore/errgroup` пустой).
- **Сценарий:** массовый resume парка (перезапуск VPN-сервера) → N одновременных горутин, каждая держит TG-вызов до 10с; TG 429 → горутины копятся.
- **Смягчение:** ctx привязан к shutdown (`relayParent(d)`), так что graceful-shutdown их погасит; события не на каждый отчёт, а на resume/deploy.
- **Фикс:** bounded worker-pool / семафор фикс. ёмкости; при переполнении — `slog.Warn` + drop.

### DEP-01 — Restore: нет авто-отката после `systemctl stop` `[Medium]`

- **Где:** `cmd/deploy/restore_backup.go:573-585` (`buildRestoreRemoteScript`).
- **Что подтверждено (улучшение):** `PRAGMA integrity_check` по state.db и `test -s` обоих токенов идут **до** `systemctl stop` (`:575-577`); `backend.yaml` парсится/валидируется локально в `InspectRestoreBackup` (`validateRestoreBackendYAML`) **до** загрузки. Это закрывает главную часть прежнего DEP-01.
- **Остаётся:** при `set -eu` если `install` падает **после** stop (диск полон, inode, права) — скрипт обрывается, сервис остаётся DOWN, `.bak`-копии есть, но авто-`systemctl start` старой версии нет.
- **Фикс:** `trap` на ERR/EXIT после stop — восстановить из `.bak` и запустить старую версию; сделать health-check (`:587-611`) обязательным с retry.

## 4. КРИВАЯ ЛОГИКА / ЗАМЕТКИ (работает, но требует внимания)

## 8. ОТКЛОНЁННЫЕ КАНДИДАТЫ (разведка дала, верификация не подтвердила)

- **«dispatch использует `r.Context()` — CRITICAL»** (`handler.go:709`) — ложно: это синхронная работа внутри запроса; `http.Server.Shutdown` дожидается активных запросов, ctx не обрывается раньше времени.
- **«ensureTopic создаёт дубль топиков»** — ложно: мьютекс сериализует, `EnsureTopicForUser` персистит thread_id до релиза лока, второй double-check ловит (`topics.go:54`).
- **«maint-токен можно заблокировать race'ом чужого member'а»** — не подтверждено: токен привязан к `UserID`(+`ActorTGID`), консьюм чужого юзера не удаляет токен.
